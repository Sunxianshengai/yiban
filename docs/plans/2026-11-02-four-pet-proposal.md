# 忆伴四位独立桌宠伙伴方案

日期：2026-11-02。状态：产品与实现提案；未修改业务代码，未生成动画或提交付费任务。

## 已确认的范围

- 以桌面 `桌宠` 文件夹的四张母图为准：狐狸娘、困困绵羊、机械猫、蝙蝠魔女。角色名称可另定，已有旧方案中的小满单角色不作为本次范围。
- 四位是独立 AI 伙伴，各有人格、私人长期记忆、会话、音色和关系进度。
- 同时提供 Windows 桌面悬浮与网页内宠物。普通网页活动范围在页面内；Windows 悬浮由 Electron 实现。
- 同时支持单宠常驻切换、多宠同屏两种模式；同屏可分别显示或隐藏四位伙伴。
- 动作目标接近 dsh-pet 的丰富程度，按批次制作；通过现成工具与流水线减少重复提示、模型调用和返工，维持最终动作质量。
- 动画服务尚未确定，优先复用用户已有账号；本轮不需要购买服务或开始批量生成。

## 1. 四位伙伴的身份

角色模板只存默认形象、人设与动画气质。首次启用时，为当前用户创建自己的伙伴实例，创建过程幂等；全站用户不共用四条伙伴数据。

建议人设方向（供后续编辑）：

| 形象 | 默认交流气质 | 独有动作方向 |
| --- | --- | --- |
| 狐狸娘 | 温暖、机灵、爱回应 | 摇尾、探头、抱尾巴、开心小跳 |
| 困困绵羊 | 温柔、慢节奏、善于倾听 | 揉眼、打哈欠、抱枕、蜷缩睡觉 |
| 机械猫 | 好奇、爽快、喜欢一起动手 | 调护目镜、检查小工具、尾巴摆动、得意叉腰 |
| 蝙蝠魔女 | 有主见、俏皮、轻度傲娇 | 整理帽檐、收展翅膀、小魔法、抱臂偷看 |

这只是角色模板，不根据动物外观编造用户经历。每位的语气、称呼、主动程度和音色允许分别调整。

身份、会话、私人记忆、草稿、未读、开场话头以 `userId + profileId` 为作用域。共享账号基本设置可以复用；另一位伙伴的私聊内容不自动进入当前伙伴的上下文。家庭档案作为单独可授权的资料来源，由用户决定允许哪些伙伴引用。

现有代码需要补齐两点：`chat-callbacks.mjs` 的旧 knock 开场与话头去重尚有仅按 userId 扫描的路径，应加入伙伴过滤；伙伴创建校验目前围绕现实家庭角色，应增加虚构伙伴类型，避免给桌宠强塞现实亲属关系。

关系进度独立保存初次相遇、相处天数、偏好、动作解锁等，不复用现实关系评分，不把每次摸摸或随机动作写入长期记忆。四位共用现有模型服务，以不同人格和上下文调用，无须部署四套模型。

## 2. 使用与多宠模式

设置增加“桌宠伙伴”：四位卡片、启用、单宠/多宠、尺寸、停靠/漫游、音量与免打扰。单宠模式切换时保留每位聊天与位置；多宠模式允许任选一至四位出现。

- 点击伙伴：短互动反馈，打开对应伙伴的迷你聊天；同一迷你窗切换内容时清楚显示当前角色。
- 拖动：角色跟随、轻微弹性，轻放不抛；快速甩动的抛掷效果作为独立开关。拖动与点击通过移动阈值区分。
- 右键菜单：聊天、回主聊天、指定动作、睡觉/叫醒、固定/漫游、隐藏、设置。
- 气泡：已保存的新消息可以提示，点击定位原会话与消息，不复制聊天历史。
- 同屏：分别维护角色状态和位置，空闲动作错峰，避免四只同步重复；相互招呼先用本地短动作，不自动启动四份模型对话。
- 音频：同一设备统一排队，只有实际播放的那位进入说话状态；全局勿扰和通知频率上限约束四位总量。
- 桌面：关闭主窗可收至托盘继续；隐藏与退出区分清楚，托盘能找回任意伙伴。
- 网页：避让输入框、菜单与弹窗；手机提供可收起的停靠入口，多宠优先通过列表切换，避免占满屏幕。

## 3. 状态与动作调度

dsh-pet 的状态、动作池、睡眠和物理作为实现参照，实际业务事件来自忆伴。上游的 thinking/working/result/waiting 等任务状态不可不经映射直接套在陪伴聊天上。

| 触发条件 | 桌宠表现 | 恢复规则 |
| --- | --- | --- |
| 空闲 | 呼吸、眨眼、低频角色专属动作 | 权重抽取并避免连续重复 |
| 输入或录音活动 | 倾听、抬头 | 活动停止后回当前业务状态 |
| 请求已受理、尚无可见回复 | 思考 | 首段可见文本到来时切换 |
| 回复正在输出 | 写字或回应 | 输出结束后等待真实任务终态 |
| 提交与结算中 | 短等待 | completed 才结束，不提前庆祝 |
| 音频正在播放 | 说话 | 依据播放、暂停、结束事件 |
| 新的真实未读 | 短招手/举信封，保留角标 | 实际读到对应消息才已读 |
| 新任务成功完成 | 点头、短庆祝 | 每任务一次，历史恢复不重播 |
| 失败或断网 | 轻疑惑＋可操作提示 | 不无限保持失败动作，重试由用户触发 |
| 用户停止 | 收起动作 | 回到待机，不表演失败 |
| 拖动、甩抛、落地 | 拖动态、物理反馈 | 结束后重新计算实时业务状态 |
| 睡觉 | 入睡→睡眠循环→醒来 | 三段配套；睡眠是安静模式，保留消息接收 |
| 锁屏或系统休眠 | 暂停动画、漫游与声音 | 恢复先同步快照，再继续 |

业务状态、短互动、气泡和未读分开管理。用户主动操作优先；收到新消息不应强制打断拖动或语音。终态按 job.status 判断，不能把 SSE done 一律当成功。取消、重试、乱序与迟到事件都需要明确回收；切换账号清除旧账号内容。

## 4. 动作分批计划

第一步先为一位伙伴制作待机、点击和睡眠等少量样片，确定透明边缘、角色一致性、脚底和循环接缝。样片通过后，同一规范覆盖全部四位；不以只完成一位替代四位交付。

建议每位分三批：

1. **基础可用：**待机呼吸与眨眼、招手、点击回应、拖动、思考、说话、入睡、睡眠循环、醒来。部分状态初期可有明确降级动作。
2. **完整联动：**倾听、回复中、收到消息、庆祝、疑惑、散步与转向、伸懒腰、玩耍。
3. **丰富表现：**每位追加多套待机/互动变体和专属动作，按每位约 16 段、32 段再逐批扩充。最终以对标 dsh-pet 的动作类别与确认的变体清单为验收依据，不把某个较少的段数当作上限。比如后续确认每位 64 段，就应交付四位共 256 段实际通过验收的视频；这只是规模举例，不是上游动作总数或本轮已确定数量。

动画段数与程序状态数量不同：一个状态可轮换多段动作；拖拽位移、抛物线和弹性由程序处理，不为每个速度生成一条视频。

## 5. 现成工具与制作流水线

上游官方制作说明推荐图生视频，列出可灵、Runway、豆包；其实际素材采用豆包生成，短动作独立生成，再抠像、归一化和编码。上游明确成品走过人工抠像，不能把其自动脚本视为全部素材已验证的高质量自动方案。[官方制作说明](https://github.com/PC2005-cloud/dsh-pet/blob/58a69ba6d0427e6dd4141bee419414020070cea2/MAKE-YOUR-OWN-PET.md)

推荐流水线：

`角色母图 + 动作任务表 → 图生视频 → 验收动作 → 抠像 → 尺寸/脚底归一化 → 循环与衔接检查 → 透明 WebM + manifest → 网页/Windows 验收`

工具选择：

- **优先用户已有的豆包/即梦、可灵或 Runway 账号。** 先用同一角色和少量相同动作比样片，再决定批量路线；不要求同时购买多家。
- **Runway 已安装并验证认证成功。** 当前连接的工作区为 Free，查询返回可用视频模型为空、余额为零，因此目前不能通过该账号生成动作视频；背景去除能力列为可用，但尚未执行，不代表已经验证透明边缘质量。可选择升级后试样片，或沿用用户已有的豆包/可灵生成源视频；耳尾、翅膀边缘质量仍需样片验证。本次查询未提交生成、上传或扣费任务。
- **ComfyUI + Wan 为可控批处理备选。** 官方已有 I2V/首尾帧 JSON 模板；服务器队列可固定工作流，只替换母图、动作文本和种子。机器当前 GPU 为 GTX 1650 4GB，不把本机大视频模型批量生成作为首选；如果采用此线，优先评估云 GPU 或用户已有环境。[官方模板](https://docs.comfy.org/tutorials/video/wan/wan2_2)、[队列接口](https://docs.comfy.org/development/comfyui-server/comms_routes)
- **现有 imagegen 用于必要的关键帧与角色一致性修正。** 它不等同于视频生成器。现有 dsh-pet 抠像、缩放、转码脚本可审核后适配，工具路径、输入尺寸、睡眠锚点和失败检测需要修正。
- **FFmpeg/剪辑工具负责确定性后处理。** 不用大模型逐帧重新生成透明背景或重复讲解同一套加工步骤。本机 PATH 尚未发现 FFmpeg，实施素材流水线时再选择安装或指定已有版本。

控制质量：固定镜头、单角色、完整耳尾帽翼与鞋子、统一画幅、固定脚底，普通动作尽量回同一站姿；睡觉使用睡姿基准。首尾图相同只能提高控制性，仍需检查姿态漂移、速度接缝和中间变形。不能把所有循环简单倒放，避免眨眼、走路和说话不自然。[Runway 图生视频指南](https://help.runwayml.com/hc/en-us/articles/48324313115155-Image-to-Video-Prompting-Guide)

## 6. 减少 token 与生成费用的方法

- 人格模板、动作规范与任务表一次确认后落盘复用，后续只传角色 ID、动作 ID 和变更项，避免每个素材重发整套讨论。
- 视频在制作时生成一次，运行时本地播放；待机、点击、拖拽、睡眠和普通短回应使用本地调度，不请求模型。
- 四位各有上下文，只向当前聊天伙伴发起请求；相互打招呼使用本地演出。真实 AI 群聊若要增加，单独明确触发方式与费用。
- 主动联系继续使用现有调度与账号级频率限制，不为四只各加一套高频碎碎念模型任务。
- 用任务清单记录 prompt、母图版本、服务/模型、参数、种子、结果路径和验收状态；支持断点续跑，只重做失败动作。
- 程序化检查尺寸、时长、解码与透明通道，再人工/视觉抽检动作；高风险动作（耳尾翼、快速转身、落地）重点验收，不降低统一质量标准。
- 镜像仅用于确实适合的动作，避免机械工具、左右眼异色和不对称服饰被错误交换；多套真实变体逐步补足。

## 7. 技术落点与实施阶段

继续使用 Next.js + React + Electron。提取共享聊天运行层；四位伙伴共用连接与窗口协调能力，各自维持会话状态。Windows 增加一个常驻运行层、每位一个局部透明窗口、复用的迷你聊天窗及托盘。网页与桌面共用角色包和动作规则；Electron 窗口位置、穿透和多屏由主进程处理。

素材保留本地离线待机能力。当前安装包只打包 `electron/**/*`，需要明确包含角色资源。透明不等于自动穿透，要独立处理角色、气泡与菜单命中。多宠按可见数量控制解码与动作频率；后台降低频率但不伪造在线聊天状态。

| 阶段 | 交付与通过条件 |
| --- | --- |
| A 样片与窗口验证 | 一位少量动作跑通透明、循环、拖动与DPI；选定视频制作工具 |
| B 四伙伴身份与会话 | 四套用户专属人格/记忆/音色，修复开场话头串台，共享运行层接管真实聊天 |
| C 双形态与双模式 | 网页/Windows，单宠切换/多宠同屏，迷你聊天、托盘、位置恢复 |
| D 全部四位基础动作 | 四位均能完整使用基础互动、聊天联动与三段睡眠 |
| E 丰富动作与发布验收 | 批量补充变体/专属动作，通知去重、音频队列、账号隔离、多屏与安装包回归 |

主窗隐藏但忆伴进程运行时可继续聊天；完全退出、断网或休眠的恢复需按服务端原 job 状态处理，不承诺退出后模型仍持续生成，不自动重发导致二次扣费。
